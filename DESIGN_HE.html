FunnelIQ: מדאטה של משפך שיווקי למוצר פרוס עם לוגין

זה מסמך התכנון (design) של הפרויקט. הוא סוגר את כל ההחלטות הארכיטקטוניות לפני שורת קוד אחת. אחרי שתאשר אותו, אכתוב ממנו את PLAN.md המפורט (תחנות עבודה, שערי בדיקה, סימני כשל) בדיוק כמו ב-Northwind. בסוף המסמך יש רשימת החלטות ממוספרת שאתה מאשר או דוחה אחת-אחת.

ריפו: git עצמאי + GitHub ציבורי שרת: FastAPI דפדפן: HTML/JS + Chart.js (React אופציונלי בסוף) ML: סקריפטים + בדיקות סביבה: conda AI_dev חשבונות Supabase + Railway: קיימים

מה הברייף מודד בפועל (תזכורת קצרה)

  • שלושה עמודי תשתית: GitHub (README, קומיטים קטנים, PR, Actions), Supabase (טבלה + טעינה חוזרת + Auth + RLS), Railway (URL ציבורי, משתני סביבה, health check, פריסה אוטומטית מ-push).
  • שש חבילות אנליטיות: EDA וניקוי, רגרסיה ל-ltv_months, סיווג upsell, ציון super customer מ-referred, פרדוקס המעקבים, אופטימיזציית תקציב של ₪50,000.
  • הבר: זר פותח את ה-URL, מתחבר, מקבל חיזוי ללקוח חדש, רואה את תובנות המעקבים והתקציב וקורא את ההמלצות. בלי שתיגע בכלום.

01שלוש החלטות ארכיטקטוניות פתוחות

בכל אחת יש חלופות אמיתיות. הצגתי אותן עם המלצה מנומקת. כל השאר במסמך נגזר מההמלצות האלה.

החלטה A: איך המידע מגיע מ-Supabase למשתמש (הלב של דרישת ה-RLS)

הברייף דורש ש-מסד הנתונים עצמו יאכוף שרק משתמש מחובר קורא דאטה (Row Level Security), ושהקריאות יגיעו עם הטוקן של המשתמש המחובר. שרת שקורא הכל עם מפתח ה-service עוקף את זה.

A1: כל הדרך דרך ה-API, עם הטוקן של המשתמש

הדפדפן מתחבר עם supabase-js (anon key), מקבל JWT, ושולח אותו בכל קריאה ל-FastAPI. השרת מאמת את החתימה, ואז פונה ל-Supabase עם אותו טוקן. Postgres אוכף את ה-RLS. מפתח ה-service לא קיים על השרת ב-Railway בכלל, רק בסקריפט הטעינה המקומי.

  • נקודת כניסה אחת, RLS נאכף באמת, הרשאות מינימליות. בדיוק לשון הברייף.
  • צריך אימות JWT בשרת (ספרייה קטנה, PyJWT).

A2: הדפדפן קורא ישירות מ-Supabase, ה-API רק לחיזויים

  • פחות קוד שרת.
  • לוגיקת דאטה מתפצלת בין JS ל-Python; ה-API "לא קורא מ-Supabase בזמן ריצה" כפי שהברייף דורש.

A3: ה-API קורא הכל עם service key

  • נפסלת. הברייף אומר במפורש שזה עוקף את ה-RLS.

החלטה B: איפה המודלים המאומנים חיים

B1: אימון מקומי, קבצי מודל מקומטים בריפו

סקריפטי אימון מייצרים models/*.joblib וקובץ מטריקות JSON. הקבצים קטנים (מגה-בייטים בודדים). Railway פורס אותם עם הקוד. כל קומיט של מודל הוא גרסה שאפשר לחזור אליה.

  • פריסה דטרמיניסטית, אתחול מהיר, "איזה מודל ענה" תמיד ידוע.
  • אימון מחדש דורש קומיט מחדש. זה למעשה versioning, לא חיסרון.

B2: אימון בזמן העלייה של השרת

  • אתחול איטי ב-Railway, תוצאות שונות בין פריסות, קשה לשחזר.

B3: Supabase Storage

  • עוד מנגנון בלי תועלת אמיתית בגודל הזה.

החלטה C: מבנה האפליקציה

C1: שירות אחד. FastAPI מגיש גם את ה-API וגם את קבצי ה-HTML/JS

  • פריסה אחת ב-Railway, URL אחד, בלי CORS. אם React יגיע בסוף, ה-build שלו פשוט מחליף את תיקיית ה-static.

C2: שני שירותים (API + אתר סטטי)

  • מיותר עכשיו. רלוונטי רק אם React יגיע.

עיקרון מפתח: מפתח ה-service לא עולה ל-Railway

השרת המפורס מחזיק רק URL + anon key + מפתח ציבורי לאימות JWT. אין לו יכולת לעקוף RLS גם אם ירצה. מפתח ה-service נמצא רק ב-.env המקומי, לשימוש סקריפט הטעינה. זו הדגמה ישירה של "anon בדפדפן, service בשרת" בגרסה המחמירה שלה, וזה נימוק יפה לראיון.

למה חבילה נפרדת ל-ML ולא בתוך ה-API? כי אותו קוד ניקוי ופיצ'רים חייב לרוץ גם באימון וגם בשירות. אם ניקוי ה-CSV חי בסקריפט אחד וה-API מנקה אחרת, המודל מקבל קלט שהוא לא ראה מעולם. ml/data.py ו-ml/features.py הם מקור האמת היחיד.

04מסד הנתונים והאימות

סכמה

  • funnel_records: 19 עמודות המקור + id (מספר השורה ב-CSV, כדי שטעינה חוזרת תהיה דטרמיניסטית) + עמודה מחושבת budget_tier (Low ≤1500 · Mid 2000–5000 · High >5000) + referred כ-boolean.
  • ערכים חסרים ב-ltv_months ו-cumulative_profit נשמרים כ-NULL. הניקוי לצורכי מודל קורה ב-Python, לא במסד. ככה ה-EDA יכול לספור בדיוק כמה שורות חסרות.
  • prediction_log: user_id, model, input jsonb, output jsonb, created_at. כל חיזוי שמשתמש מבקש נרשם. זה נותן לאפליקציה גם כתיבה ל-Supabase בזמן ריצה, לא רק קריאה, ומאפשר בדשבורד "החיזויים האחרונים שלי".

מדיניות RLS

  • funnel_records: SELECT מותר ל-authenticated בלבד. אין INSERT/UPDATE דרך ה-API (הטעינה היא עם service key שעוקף RLS בכוונה, מקומית).
  • prediction_log: INSERT ו-SELECT רק על שורות שבהן user_id = auth.uid().
  • הוכחה בשער הבדיקה: שאילתה עם anon key בלי טוקן מחזירה 0 שורות; עם טוקן של משתמש מחובר מחזירה 3,500.

זרימת הלוגין

  1. מבקר לא מחובר רואה רק את login.html. הדשבורד בודק session בטעינה ומפנה ללוגין אם אין.
  2. supabase-js (עם anon key, שמגיע מ-GET /api/config כדי שלא יהיה hard-coded בקובץ סטטי) עושה signInWithPassword.
  3. כל fetch לדשבורד שולח Authorization: Bearer <access_token>.
  4. app/auth.py מאמת את החתימה מול ה-JWKS של הפרויקט (Supabase החדש חותם ב-ES256; נשמור fallback ל-HS256 עם SUPABASE_JWT_SECRET למקרה של פרויקט ישן). בלי טוקן תקף: 401.
  5. app/db.py יוצר לקוח supabase ומצמיד אליו את הטוקן של המשתמש, כך שכל שאילתה עוברת RLS.
  6. Sign-out מנקה את ה-session בדפדפן ומחזיר ללוגין. הרשמה עצמית כבויה בהגדרות Supabase; משתמשים נוצרים ידנית ב-dashboard של Supabase (זה כלי פנימי).

05העבודה האנליטית: שש החבילות

מדיניות דליפה (leakage): מה מותר להיות פיצ'ר בכל משימה

הכלל: פיצ'ר לגיטימי רק אם העסק מחזיק אותו ברגע החיזוי. נגדיר ב-ml/features.py שתי קבוצות, ובדיקה אוטומטית (leakage guard) שנכשלת אם מודל מנסה להשתמש בעמודת תוצאה בלי היתר מפורש.

  • FUNNEL (זמן רכישה): ad_budget, num_leads, leads_answered, leads_not_answered, followup_1..5, not_closed, closed, calls_to_closed, calls_to_not_closed, customer_acquisition_cost. פלוס פיצ'רים מהונדסים: answer_rate, conversion_rate (closed/num_leads), cost_per_lead, budget_tier.
  • OUTCOMES (תוצאות): ltv_months, purchased, upsell, cumulative_profit, referred. לעולם לא פיצ'ר, אלא אם יש הצדקה כתובה לאותה משימה.
חבילהמטרהפיצ'ריםמה נחשף באפליקציה
P1 חקירה וניקוילהבין את הדאטה לפני שסומכים עליו—פאנל Overview: חסרים, מתאמים ל-profit, עקומת תקציב←לידים, המרה לפי tier
P2 רגרסיהltv_monthsFUNNEL בלבד. cumulative_profit מוצא: הוא נצבר לאורך החיים, כלומר הוא תוצאה של ltv. נריץ ניסוי ablation "עם profit" רק כדי להראות את ה-R² המנופח כראיה בדוח.טופס "לקוח חדש" ← חיזוי חודשים + השוואת 3 המודלים + חשיבות פיצ'רים
P3 סיווגupsellשתי גרסאות: early (FUNNEL) ו-tenure-aware (FUNNEL + ltv_months). ההצדקה לשנייה: פנייה ל-upsell נעשית ללקוח קיים, שהוותק שלו ידוע. הכלל העסקי בברייף עצמו משתמש ב-LTV. נדווח על שתיהן, נשרת את זו שמנצחת עם הצדקה כתובה.הסתברות upsell + הכלל העסקי מול המודל (איפה כל אחד מנצח)
P4 super customerreferredFUNNEL + budget_tier קטגורי ב-CatBoost (טיפול נייטיבי). כוונון: learning rate × depth × iterations, 5-fold stratified.ציון 0–100 + פרופיל ה-super customers (נתח מהרווח, CAC ממוצע)
P5 פרדוקס המעקביםלבדוק את טענת מנהל המכירותסטטיסטיקה תיאורית: נשירה בכל שלב, מספר מעקבים לעסקאות שנסגרוגרף נשירה + המלצה מנוסחת
P6 אופטימיזציית תקציבcumulative_profit ← סימולטורFUNNEL. הסימולטור מקבל רק תקציב, וממלא את שאר הפיצ'רים מ"פרופיל טיפוסי" (חציון) של כל רמת תקציב. הדאטה מכיל בדיוק 16 רמות בדידות (500 עד 20,000), אז הפרופיל מוגדר היטב.סימולטור: בוחרים חלוקה של ₪50,000 ← רווח צפוי + השוואת אסטרטגיות + המלצה

הערות מתודולוגיות שיכריעו בשלב ה-EDA (לא עכשיו)

  • purchased: 337 שורות עם 0. אם ללקוחות שלא רכשו יש בכל זאת ltv ו-profit, זה סימן לרעש בדאטה. הצעה: מודלי P2/P3/P4 מאומנים על לקוחות בלבד (purchased = 1), עם תיעוד. ההכרעה אחרי בדיקה.
  • ערכים חסרים: רק 33 שורות (4 ב-ltv, 29 ב-profit). ברירת מחדל: להשמיט אותן מהאימון של המשימה שבה זו עמודת המטרה, ולהשאיר אותן בכל השאר. לא לבצע imputation לעמודת מטרה.
  • איזון מחלקות: upsell = 42% חיובי, referred = 39% חיובי. שתיהן מאוזנות סבירות, אז ההשערה היא ש-scale_pos_weight לא נדרש. נבדוק עם ובלי, ונתעד.
  • כפילות של המשפך: closed + not_closed ו-leads_answered + leads_not_answered כנראה קולינאריים. לעצי boosting זה לא מפריע, אבל זה ישפיע על פרשנות החשיבות. יתועד.

מסכי הדשבורד (דף אחד, ניווט בלשוניות)

  • Login: אימייל + סיסמה, הודעת שגיאה, כפתור sign-out בכל מסך.
  • Overview: כרטיסי KPI (שורות, חסרים, המרה כוללת), גרף תקציב←לידים, המרה לפי tier, מתאמים ל-profit.
  • Predict: טופס לקוח חדש ← שלושת החיזויים בבת אחת (LTV, upsell, super score) עם הסבר קצר וחשיבות פיצ'רים.
  • Follow-ups: גרף נשירה, מספר מעקבים לעסקאות שנסגרו, ההמלצה.
  • Budget: הסימולטור. אסטרטגיות מוכנות (2×20k+10k · 10×5k · 25×2k · 100×500) + בונה חלוקה חופשי שחייב לסכום ל-50,000.
  • Findings: ההמלצות העסקיות (מ-REPORT.md) + טבלת המודלים והמטריקות.

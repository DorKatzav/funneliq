התוכנית סימנה React כ-M9 אופציונלי, "רק אם נשאר זמן". הפרויקט הושלם והברייף מכוסה בממשק הוואנילי הנוכחי. המסמך הזה עונה על שלוש שאלות: מה React היה נותן למשתמש שאין לו היום, מה הוא לא היה משנה, ומה המחיר בשעות, בשלוש רמות היקף.

בשפה פשוטה

React הוא ספריית ממשק שמפרקת את המסך לרכיבים עם "מצב" משלהם, במקום קובץ אחד שמעדכן את הדף ידנית. בפרויקט הזה הוא לא ישנה אף מספר ואף תשובה למייסד: השרת, המודלים והאבטחה נשארים כמו שהם. מה שהוא כן ישנה: איך הממשק מרגיש (ניווט עם כתובות, ולידציה בזמן הקלדה, תוצאות שנשמרות בין מסכים, טפסים חכמים יותר) ועד כמה קל להוסיף מסך שישי ושביעי בלי לשבור את החמישה הקיימים. ההמלצה בתחתית: לא לעשות את זה כחלק מההגשה; לעשות אותו רק אם הכלי ממשיך לחיות אחרי הקורס או אם רוצים אותו כפריט תיק עבודות, ואז בהיקף "זהות מלאה" עם תיבת זמן.

1. מה יש היום, ואיפה זה נחלש

הסטאק: static/dashboard.html (~750 שורות, כולל ה-JS), app.js (session + fetch), styles.css, Chart.js ו-supabase-js מ-CDN. בלי שלב build: מה שב-git הוא מה שרץ. זה יתרון אמיתי: פריסה של שירות אחד, בלי node ב-Railway, ובלי "עובד אצלי".

איפה זה נחלש (מה שראינו במהלך העבודה, לא ספקולציה):

  • לשוניות בלי כתובת. חמשת המסכים הם section hidden; אין URL ללשונית, כפתור "אחורה" לא עובד, ואי-אפשר לשלוח לינק ל-"Budget".
  • גרפים בלשוניות מוסתרות. Chart.js על canvas שנוצר בלשונית נסתרת דרש תיקון ידני של resize + update (M6). ב-React הגרף נוצר כשהרכיב מוצג, והבעיה לא קיימת.
  • ולידציה רק בשרת. משפך לא עקבי מוחזר כ-422 עם הודעה יפה, אבל רק אחרי לחיצה. אין סימון של השדה הבעייתי תוך כדי הקלדה.
  • אין מצב משותף. הלקוח שחזיתם בלשונית Predict לא "קיים" ב-Findings או ב-Budget; כל מסך שולף לבד. הקוד מעדכן DOM ידנית ב-40+ נקודות (getElementById).
  • מטמון. אחרי פריסה הדפדפן הגיש dashboard.html ישן (M7); תוקן ב-Cache-Control: no-cache. ב-build של Vite הקבצים מקבלים hash בשם, והבעיה נעלמת מבנית.
  • תחזוקה. קובץ אחד גדול בלי טיפוסים ובלי בדיקות UI. הוספת מסך שישי פירושה עוד 150 שורות באותו קובץ.

מה React לא ישנה

לא את התשובות (P1–P6), לא את המודלים, לא את ה-API (הוא נשאר בדיוק כפי שהוא: זה היתרון הגדול של ההפרדה שבחרנו ב-D3), לא את האבטחה (אותו JWT, אותו RLS; supabase-js עובד ב-React בדיוק כמו היום), ולא את הפריסה מבחינת המשתמש (עדיין URL אחד ב-Railway). כל פריט בטבלה למעלה אפשרי גם בוואנילה; React רק הופך אותו לזול פי 2–3 לכתוב ולתחזק.

3. כדאיות: מתי כן ומתי לא

לא כדאי, אם

  • הפרויקט נגמר בהגשה. הברייף מכוסה; React לא מוסיף אף תשובה ואף נקודת הערכה מובהקת מלבד "סטאק מודרני".
  • אין 12+ שעות פנויות. React חצי-גמור גרוע מוואנילה שלם: שני ממשקים לתחזק.

כדאי, אם

  • הכלי ימשיך לחיות ומישהו יבקש מסך שישי (למשל דוח חודשי אוטומטי או ניהול משתמשים). אז הקובץ הבודד הופך לצוואר בקבוק.
  • רוצים את הפרויקט כפריט תיק עבודות של full-stack: FastAPI + React + Supabase הוא סטאק שמראיינים מזהים.
  • המייסד באמת ישתמש בזה בטלפון או יצטרך עברית.

הסיכונים העיקריים

  • Build בפריסה. צריך node. שתי דרכים: (א) GitHub Actions בונה את frontend/ ומקמט את static/ (פשוט, אבל קומיטים אוטומטיים); (ב) Railpack עם node + python באותו image (יותר "נכון", יותר שברירי; ראינו כבר שני תיקוני פריסה ב-M1 וב-M3).
  • שני ממשקים במהלך המעבר. חייבים תיבת זמן וקו סיום ברור: הוואנילה נמחק רק כשה-React עובר את מבחן הזר.
  • גרפים. Recharts יפה יותר אבל דורש כתיבה מחדש של כל גרף; react-chartjs-2 שומר את Chart.js הקיים ומקצר.
